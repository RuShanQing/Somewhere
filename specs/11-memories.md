## MEMORY-01 定位与边界

纪念册不是聊天记录的镜像，也不是自动公开的社区内容：
- **双城日记**：一次完整双向生活片段交换形成的私人配对页面。
- **共同手帐**：双方明确授权、可以共同维护的长期作品（P1），可标注重要时间并在未来加入画、歌等小惊喜。
- **个人记忆**：只属于自己的独立记录，可来自自己的日常或经合法授权保留的内容。

三者存储与权限模型独立。任何私人材料**不能因为被收录进纪念册就自动成为公开城市故事**。

## MEMORY-02 双城日记的生成规则（P0）

1. 在同一段共途中，A 的一张明信片和 B 的对应回复都已经 `DELIVERED`。
2. 回复记录 `replyToPostcardId`，指向被回应的信；服务端判断二者是否属于同一共途、不同作者和有效双方权限。
3. 后台生成 `diary_pages(id, passage_id, postcard_left_id, postcard_right_id)`，唯一键防止重复形成同一对卡片。
4. 页面按两座城市的故事排列，呈现双方当时自愿提供的文本与城市级标签。
5. 未送达时**不能**通过日记接口提前读取第二张明信片的内容。
6. 一次交换结束已形成完整页；无需双方成为信友，也无需保证下一轮通信。

展示顺序建议按最早寄出、城市、时间确定，而不是随机重排。作者后续搬家不修改该页历史城市信息。

### 形态（2026-10-30 已确认）

双城日记是“册 / 页 / 左右”三层，不是持续追加的流水账：

- **册 = 一段共途**：由 `passage_id` 决定，提供主题与双方；
- **页 = 一次完整交换**：`diary_pages` 一行，`left = 被回信的原信`，`right = 回信`；
- **左右 = 两封信**：只读正文、寄出时间与城市级信息。

同一段共途内发生多次交换时，**每次回信生成一张新的独立双页**；旧页不改写、不追加、不合并。相邻两页可以共享一封信（上一页的右页是下一页的左页），这是“回合”结构，不是重复存储。`ONE_OFF` 共途通常只有一页，`ONGOING` 共途会随时间累积多页。

不提供手动创建、追加、合并、编辑入口；需要双方共同编辑与历史版本的场景属于 MEMORY-05 共同手帐（P1）。

### 生成条件与口径

- 生成只看投递事实：`right.reply_to_postcard_id = left.id`、两封均 `DELIVERED`、同一 `passage_id`、不同作者；`left` 必须是较早寄出的原信。
- `passages.progress_status` **不参与**判定，依据 PASSAGE-03 的三状态分离；PRD MEM-01 的“仅已完成共途生成”按“已完成的双向交换”理解。
- 同一封回复只生成一页：唯一键 `(postcard_left_id, postcard_right_id)` + 幂等写入，Worker 重试与并发扫描不重复。
- 页面只保存两封明信片的引用，不复制正文；读取时由 `PostcardReader` 重新校验状态与参与者。
- 读取时若任一封不再是 `DELIVERED`（例如 `RESTRICTED`），页面不返回正文，列表同步隐藏。

## MEMORY-03 双城日记的权限

| 操作 | 双方参与者 | 第三方 | 备注 |
|---|---|---|---|
| 阅读已完成的日记页 | 在双方拥有被授予的阅读权时允许 | 拒绝 | 账号、封锁和删除政策优先 |
| 编辑原信内容 | 不允许 | 不允许 | 发送后的原文不可改 |
| 删除自己的派生收藏视图 | 允许 | 不允许 | 不擅自删除对方独立持有的记录 |
| 公开发布日记页 | 需要逐项单独授权 | 默认禁止 | 不能从“已共同拥有”推导公开许可 |
| 导出包含对方内容的作品 | 按明确授权与隐私政策 | 不允许 | P0 可不提供导出 |

共途完成、归档、停泊与信友撤销不自动清空历史；但法定删除、内容违规、撤回特定公开授权等需遵循 SafetyModule 的专项处理。

> 2026-10-30：上表的“允许删除自己的派生收藏视图”是长期权限边界，**不代表 TASK-013 已提供删除接口**；本阶段不实现日记删除、软删除或 `hidden_at` 字段。

## MEMORY-04 个人记忆（P0）

`personal_memories(id, owner_id, title, body, source_type?, source_id?, created_at, updated_at)`。

- 用户手动创建/编辑/删除只属于自己的记录，默认 `PRIVATE`。
- 若引用已收到的明信片，只记录引用与可见性判断，不把对方原文偷偷复制成可以公开发布的资源。
- 用户可以把个人记忆整理成日期顺序或主题分组，但不生成必须每日打卡的机制。
- 删除本人个人记忆只删除本人视图，不影响源明信片的合法保留状态。
- TASK-011 只实现手工记录；`source_type/source_id` 未落库，避免在明信片读取授权尚未接入时制造假引用。私人性是模块级不变量，不提供 `visibility/is_public` 字段。

## MEMORY-05 共同手帐（P1）

未来数据模型：`shared_notebooks`、`notebook_entries`、`notebook_members`、`notebook_assets`。

- 双方对作品的**编辑权限**须单独确认，不等同于共途参与资格。
- 条目记录作者、版本、创建/更新时间；不允许悄悄覆盖对方修改历史。
- 重要时间标注可以单独记为事件；多媒体上传前必须规划病毒扫描、版权提示、存储清理和元数据去除。
- 一人撤销共同编辑权后，停止后续写入；历史读取按单独权限政策处理。
- 音乐资源以合法链接/授权方式引用，不自动抓取和重传受版权保护的音频。

当前 P1 不得被 TASK-001 自动实现。

## MEMORY-06 API（建议）

- `GET /api/v1/memories/diaries`：我有权阅读的双城日记页面列表；只返回元数据（所属共途主题、城市对、两封信的日期），**不返回正文**；按形成时间倒序分页。
- `GET /api/v1/memories/diaries/:id`：单页详情，返回左右两封正文；每次请求重新校验参与者身份与两封状态，非参与者、非法 UUID、任一封受限统一 404。
- 不提供 `POST/PATCH/DELETE /memories/diaries*`：页面只能由服务端生成，本阶段不提供删除、分享、导出。
- `GET /api/v1/memories/personal`：我的个人记忆。
- `POST /api/v1/memories/personal`：新建个人记忆。
- `PATCH /api/v1/memories/personal/:id`：本人编辑。
- `DELETE /api/v1/memories/personal/:id`：本人删除。
- `/api/v1/memories/notebooks/*`：P1 实施时再具体定义，不在 P0 建造假接口。

## MEMORY-07 数据完整性与异常

- 日记页面仅由真实、已送达、授权的明信片形成；不能让前端伪造“共同完成”。
- 若已到达信件因安全问题受限，派生页面不应继续泄露其正文。
- 同一封回复不会因 Worker 重试而生成重复日记页面。
- 第三方通过猜测 URL、修改 ID、搜索接口也不得读取他人的私人作品。
- 一方退出共途不能强制擦除另一方自身写作的全部合法历史；作者的隐私撤销范围需要独立明确。

## MEMORY-08 验收

- 已完成双向交换可以生成一页且只生成一页双城日记。
- 回复尚未送达时，日记详情不得出现该回复的正文。
- 相关参与者按照授权可读；其他用户无法通过任何 API 获取。
- 个人记忆默认仅本人可见，支持保存、编辑和删除。
- 关系归档不自动公开、清空或锁死既有合法记忆。
- 共同手帐在 P1 未启用前以诚实的暂未开放状态展示。
- 同一段共途的多次交换形成多页；旧页不因新回信而改变。
- 相邻两页共享一封信时不视为重复内容，存储中仍只有一份正文。
- 日记列表不返回正文；详情在任一封受限时不可读。
- 不提供手动追加、合并、编辑或公开入口。
