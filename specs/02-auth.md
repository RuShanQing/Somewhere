# AUTH · 注册、登录和会话

**优先级：P0** · 归属：AuthModule / Web Auth 页面  
首个实现任务：`tasks/current.md` 的 TASK-001。

> 实现状态（2026-10-28）：TASK-001 完成注册/登录/会话/退出；TASK-002 完成响应字段收敛与单活动会话。邮箱验证、找回密码、设备会话管理、账号删除仍未实现（见 AUTH-07）。

## AUTH-01 业务目标

允许成年人创建账号、登录、刷新页面保留会话、主动退出；用户能安全访问自己的私人邮局。注册登录是基础设施，不与任何共途或信友关系绑定。

## AUTH-02 输入、字段与基础规则

- 注册：`email`（正规化并唯一）、`password`（最少 12 字符，支持较长密码）、`nickname`（1–32 可显示字符）、`adultConfirmed=true`。
- 登录：`email + password`；失败提示不得区分“账户不存在”和“密码错误”。
- 邮箱不是公开昵称，不返回给其他用户。
- `users.password_hash` 采用 Argon2id；任何日志、审计或异常不得包含明文密码。
- 首阶段保留 `email_verified_at` 字段；邮箱验证可在公开投递前单独完成。TASK-001 不依赖真实发件服务。
- 不提供手机号、人脸、身份证或第三方 OAuth 作为首阶段必需条件。
- 公开上线前应完善邮件验证和找回密码机制；没有这些能力的演示版本不得宣称适合直接对公众部署。

## AUTH-03 API

| Method | URL | 说明 |
|---|---|---|
| POST | `/api/v1/auth/register` | 创建账户；重复提交不会创建第二个账户 |
| POST | `/api/v1/auth/login` | 创建服务器会话并设置 Cookie |
| POST | `/api/v1/auth/logout` | 撤销当前会话并清理 Cookie |
| GET | `/api/v1/auth/me` | 返回当前用户的最小个人资料或 401 |

成功响应：注册与登录返回 `{ id, nickname, cityId?, emailVerified, role }`，**不返回 email**；`role` 为 `USER | ADMIN`。`GET /auth/me` 额外返回本人 `email`（未来的本人设置接口同理）。邮箱与角色都不返回给其他用户；公开故事响应也不包含角色。所有请求参数经 DTO 验证。

错误示例：
- `VALIDATION_ERROR`（422）；`REGISTRATION_CONFLICT`（409，文案不明确指明邮箱存在）。
- `AUTH_INVALID_CREDENTIALS`（401，统一错误）。
- `AUTH_REQUIRED`（401）；`RATE_LIMITED`（429）。

## AUTH-04 Session 与安全

- 服务端生成密码学安全随机 Session Token，仅通过 `HttpOnly` Cookie 交给浏览器；数据库只存 Token 哈希。
- 生产必须 `Secure` + HTTPS，`SameSite=Lax`，明确过期与登出吊销；本机纯 HTTP 可有受控的开发专用配置。
- 写请求具备 CSRF 保护或严格 Origin 校验；不在 localStorage/sessionStorage 放 Session Token。
- 登录成功应旋转会话标识；主动退出使服务端会话无法再次使用。
- 采用**单活动会话**策略：登录成功后创建新会话并撤销该用户其他活动会话，旧设备再访问受保护接口即返回 401。同一账号多设备同时在线不在本阶段范围内。
- 会话使用固定有效期（当前 7 天），不做滑动续期；过期后回到匿名状态。
- 对注册/登录 IP + 邮箱维度实施合理限流；不要无界地保存失败密码或个人信息。当前限流为单实例内存实现，部署在反向代理后必须先配置可信代理，避免所有请求共享代理 IP。

## AUTH-05 状态

`ANONYMOUS → AUTHENTICATED → REVOKED/EXPIRED`。刷新页面不得产生新的隐式登录；Session 过期后应回到匿名状态。`emailVerified` 是账户属性，不是新的会话状态。

## AUTH-06 验收（TDD + 独立旁路）

- 新用户注册只生成一条数据库记录、密码存哈希。
- 相同邮箱的不同大小写与空格写法不会创建重复账号。
- 注册与登录响应不包含 email、密码哈希或会话 Token；只有 `/auth/me` 返回本人 email。
- 正确密码登录，刷新后 `/auth/me` 仍为本人；错误密码拒绝。
- 同一账号再次登录成功后，旧会话 Cookie 立即无法访问 `/auth/me`，数据库中该用户只保留一个活动会话。
- 退出后旧会话失效；直接访问私人 API 返回 401。
- 未携带有效凭据的用户无法进入私人业务页面。
- 注册输入、错误次数、邮箱与密码长度符合约定。
- 在前端本地存储、浏览器 URL、后端日志中找不到会话明文或密码。

## AUTH-08 平台角色与审核权限（TASK-005 已实现）

> 2026-10-28 已确认并由 TASK-005 实现：城市故事审核由**管理员**角色担任。`users.role` 使用 `USER | ADMIN`；`/auth/me` 与登录/注册响应返回本人角色；审核接口由 `RolesGuard` 强制 `ADMIN`；非生产环境通过 `pnpm --filter @somewhere/api admin:grant --email=<虚构账号>` 授予。集成测试覆盖注册不可自选角色、401/403、自审 403 与角色实时解析。

- `users.role` 使用枚举 `USER | ADMIN`，默认 `USER`。
- 注册、登录、资料修改的 DTO **不得接受** `role`；客户端提交该字段应被 DTO 白名单拒绝（当前为 422）。
- 不新增管理员登录入口；管理员使用与普通用户相同的邮箱 + 密码登录。
- `GET /auth/me` 与登录/注册响应的本人用户 DTO 增加 `role`；只返回当前用户自己的角色，不在公开故事、他人资料或审核队列中返回其他用户的角色。
- `ADMIN` 只能通过非生产环境的受控脚本或 seed 授予；不提供公开的“申请管理员”接口，也不由客户端自行切换。生产环境的角色变更属于运维操作，必须有审计。
- `role` 是账号属性，不是新的会话状态。会话每次请求从数据库解析当前角色，角色被撤销后下一次请求立即生效，不依赖重新登录。
- 城市故事审核接口要求 `ADMIN`：匿名返回 401 `AUTH_REQUIRED`，已登录普通用户返回 403 `FORBIDDEN`；前端隐藏入口不构成权限控制。
- 现有密码哈希、Cookie、单活动会话、Origin 校验、认证限流和日志脱敏规则不因角色功能改变。

验收：

- 注册请求携带 `role` 不产生管理员账号，且请求被拒绝。
- 普通用户调用审核接口返回 403，管理员返回 200；匿名返回 401。
- `/auth/me` 只返回本人 `role`；公开故事响应不含任何角色、邮箱或用户 ID。
- 角色撤销后，原会话下一次请求即失去审核权限。
- TASK-001 / TASK-002 的认证、会话轮换、Cookie、限流与日志脱敏测试保持通过。

## AUTH-09 角色与权限扩展（规划，未实现）

> 2026-10-29 已确认目标，但**代码尚未实现**。当前实际角色仍为 `USER | ADMIN`，审核接口仍只允许 `ADMIN`。完整设计、权限矩阵和分阶段顺序见 [15-roles-and-permissions.md](15-roles-and-permissions.md)。

- 正式账号角色目标为 `USER | MODERATOR | CURATOR | ADMIN`；`GUEST` 只表示未登录，不写入数据库、不创建账号、不发放会话。
- 本轮采用**单枚举 + 权限蕴含**：`ADMIN` 拥有 `MODERATOR` 与 `CURATOR` 能力；`MODERATOR` / `CURATOR` 同时拥有 `USER` 能力。暂不支持同一账号同时持有 `MODERATOR` 和 `CURATOR`；如后续需要，另做 `user_roles` 架构变更。
- 角色变更后下一次请求立即生效；`role` 仍是账号属性，不是新的会话状态。
- `MODERATOR` 审核公开故事与举报，不能管理用户、角色和平台配置，不能读取私人明信片、共同日记或个人记忆，不能审核自己的故事。
- `CURATOR` 只管理已审核、已发布、已授权且未归档的公开故事精选与专题；不能执行审核决定，不能访问私人内容。`CURATOR` 依赖独立“精选专题”Spec，当前不实现。
- `ADMIN` 管理用户与角色，但**不能查看其他用户的邮箱**：后台用户列表只返回 `id/nickname/role/createdAt`，支持按 `id` 或 `nickname` 查找，不提供 email 查询、掩码邮箱或邮箱域名。管理员本人通过 `/auth/me` 查看自己的 email 不受影响。
- `ADMIN` 也不能无条件读取私人明信片、共同日记和个人记忆；角色不构成私人内容的直通权限。
- 角色授予/撤销只能由 `ADMIN` 执行；不能授予 `GUEST`；不能降级最后一个 `ADMIN`；建议禁止修改自己的角色；每次成功变更写入 `role_changes` 审计。
- 注册、登录、资料修改 DTO 继续不得接受 `role`；前端隐藏入口不构成权限控制。
- 现有密码哈希、Cookie、单活动会话、Origin 校验、认证限流和日志脱敏规则不因角色扩展改变。

验收（未来任务执行，当前未运行）：

- 匿名访问审核/管理接口 401；`USER` 403；`MODERATOR` 可审核；`ADMIN` 可审核和管理。
- `MODERATOR` / `CURATOR` 不能访问用户与角色管理接口。
- 后台用户列表、角色变更响应、审计、日志和错误中都不出现 email。
- `ADMIN` 访问他人私人明信片/记忆仍返回 404。
- 角色变更后下一次请求生效；最后一个管理员不能降级；角色变更审计只追加。
