# SAFETY · 审核、封锁、举报与隐私保护

**优先级：P0** · 跨模块约束 · 归属：SafetyModule  
这是所有开发任务的安全基线，不可因“先实现效果”而跳过。

> TASK-009 实现状态（2026-10-29）：已实现最小封锁：`user_blocks`、`GET/POST/DELETE /api/v1/safety/blocks`，并在邮局收件人 / 草稿 / 发送与共途 `canSend` 中拦截。**未实现**：举报、完整审核处置、`RESTRICT`、封锁后隐藏已送达历史。当前封锁只阻止新的通信行为，不删除历史。
>
> TASK-010 实现状态（2026-10-30）：`PenpalPolicy` 消费 `BlockPolicy`。任一方向封锁时，信友不进入 `ACTIVE`、列表隐藏、新的同意返回 403 `CONTACT_BLOCKED`；撤销始终可用；同意行不被删除，解除封锁后按双方原 `ALLOW` 恢复。

## SAFETY-01 风险边界

Somewhere 面向成年人的陌生人异步交流；主要风险是骚扰、滥用通信权限、公开个人信息、私人记忆泄露、违规内容、冒用身份和通过接力绕过封锁。

任何可能对外展示的信息，后端必须能回答：谁创作、谁允许公开、是否审核、谁可以现在访问、如何撤回。

## SAFETY-02 内容审核

| 内容类型 | P0 默认行为 |
|---|---|
| 城市公开故事 | 提交后 `PENDING`，审核通过且进入活跃池才公开 |
| 私人明信片 | 默认私人、收件前隔离正文；举报后可进入安全处理流程 |
| 个人记忆 | 只属于作者，不自动提交公开审核 |
| 双城日记 | 私有衍生记录；安全下架源内容时同步受限 |
| 善意接力 | P1，上线前必须有审核及滥用防护 |
| 共同手帐 | P1，成员控制共享；公开传播需另行审核与授权 |

审核可以由人工、可审计规则或辅助工具完成；AI 审核不是自动信任来源。审核日志记录动作与原因，不在普通用户接口暴露审核员内部备注。

## SAFETY-03 封锁与报告

- 任意用户可针对另一个用户执行封锁，**立即禁止新的通信、持续联系及接力触达**。
- TASK-009 的最小封锁已覆盖邮局收件人、草稿、发送和共途 `canSend`；TASK-010 起同时覆盖信友列表、信友请求与 `PenpalPolicy.canContinueContact`。封锁是单向记录，但拦截对双方生效。
- 封锁既不要求说明理由，也不向被封锁者发送特殊羞辱性提示。TASK-009 不改变已送达信件的读取权；历史数据保留，解除封锁后恢复新的通信。
- 举报支持 `targetType`, `targetId`, `reason`, `details?`，用户只能提交自己有权限触达的对象；速率限制与滥用防控。
- 被举报对象在调查期间的可见性由审核策略决定，不能自动作为公开定罪。
- 后台管理员（`ADMIN` 角色，由后端授权）可查看必要证据并执行 `APPROVE/REJECT/REMOVE/RESTRICT`。
- 封锁或举报不能通过重新建立共途、信友身份、善意接力或更换公开入口绕过。

## SAFETY-04 接口

- `GET /api/v1/safety/blocks`：本人发起的封锁列表；不返回 email 或“谁封锁了我”。TASK-009 已实现。
- `POST /api/v1/safety/blocks`：封锁用户；重复调用幂等；不能封锁自己；目标不存在 404。TASK-009 已实现。
- `DELETE /api/v1/safety/blocks/:userId`：由封锁者本人解除；重复调用幂等。TASK-009 已实现。
- `POST /api/v1/safety/reports`：提交举报（未实现）。
- `GET /api/v1/moderation/queue`：仅 `ADMIN` 访问；匿名 401，普通用户 403。TASK-005 已实现。
- `POST /api/v1/moderation/stories/:id/decision`：仅 `ADMIN` 执行故事审核；匿名 401，普通用户 403。TASK-005 已实现。
- `POST /api/v1/moderation/targets/:id/restrict`：安全操作必须审计；仅 `ADMIN`（未实现）。

角色定义、授予方式和会话解析见 [02-auth.md](02-auth.md) 的 AUTH-08（当前实现）与 AUTH-09（规划）；完整四角色设计见 [15-roles-and-permissions.md](15-roles-and-permissions.md)。前端隐藏入口不构成权限控制。

管理员不得审核自己创作的故事：即使拥有 `ADMIN` 角色，对本人故事执行 `APPROVE/REJECT/REMOVE` 返回 403 `FORBIDDEN`，且不写入审核动作。该限制用于最小化利益冲突，演示和 E2E 使用两个账号。

TASK-005 已实现“城市故事审核最小闭环”：`ADMIN` 队列、通过 / 驳回 / 下架、自审拒绝与 `story_review_actions` 审计。TASK-009 已实现最小封锁与邮局/共途拦截；TASK-010 已把封锁叠加到信友授权与邮局信友来源。举报、通用安全处置和 `RESTRICT` 的实际执行仍未实现，不得在界面或文档中宣称已具备。

请求拒绝需要稳定错误码，不在 API 错误中透露举报人或内部证据。

## SAFETY-05 授权顺序（每次资源读取 / 写入）

1. 身份认证（匿名可访问公开资源除外）。
2. 本人或明确授予访问权的关系验证。
3. 封锁 / 安全限制状态。
4. 发布授权 + 审核公开状态（对公开资源）或送达状态（对私人明信片）。
5. 数据最小化输出：只返回该用户需要的字段。

前端路由隐藏按钮只是体验，不等于权限控制。管理员也不能绕过审计任意导出私人明信片。

## SAFETY-06 账号、隐私与运维

- 收集最少必要信息：邮箱、昵称、城市级设置；禁止默认索取手机通讯录、精确坐标。
- 产品首版要求成年人自声明；公开部署前依据运营地区核对适用隐私和未成年人保护法律。
- 不在日志、Trace、监控中记录密码、Token、完整正文或用户隐私详情。
- 区分逻辑撤回公开权限与实际删除数据；删除时必须考虑缓存、备份、法定保留义务，政策在上线前明确。
- 本地演示与自动化仅使用虚构账号，绝不把真实用户内容导入测试数据。
- 生产环境保管密钥、数据库凭据、Cookie 密钥与邮件令牌；不提交到 Git。

## SAFETY-07 公开故事的并发与缓存

城市故事站和地图都只能通过同一个 `ApprovedStoryReader` 查询公开集合。审核下架或作者撤回后，任何缓存路径必须失效或受权限查询控制；不能出现“站内已下架但地图仍可见”。

## SAFETY-08 验收

- 未登录访问私有邮箱、共途和记忆遭拒；修改资源 ID 不改变结果。
- 封锁立即阻止新联系，即使之前有有效信友授权。
- 未审核公开故事只对作者与审核员可见；被下架后所有公共入口均消失。
- 普通用户无法访问后台审核操作或查看投诉者信息。
- 用户只能操作本人的封锁、公开授权与私人内容。
- 个人记忆只允许本人创建、读取、编辑和删除；`ADMIN` 通过 ID 猜测也返回 404；共途、信友与封锁关系都不构成读取授权。
- 错误信息与日志无密码、会话 Cookie、密文密钥和他人私信正文。
- 在途信件始终受送达前隔离保护，不因错误或通知泄露内容。

## SAFETY-09 角色扩展规划（未实现）

> 2026-10-29 记录目标，当前代码仍只支持 `ADMIN` 审核。完整设计见 [15-roles-and-permissions.md](15-roles-and-permissions.md)。

- 计划新增 `MODERATOR`（内容审核员）；`CURATOR`（城市故事策展人）在精选专题功能立项后再加入。
- 当前故事审核仍只允许 `ADMIN`；改造为 `MODERATOR + ADMIN` 需独立任务与回归测试。
- `MODERATOR` 可以审核公开故事、处理举报（举报功能实现后），但不能管理用户、角色和平台配置，不能读取私人明信片、共同日记或个人记忆。
- `CURATOR` 只能管理已审核、已发布、已授权且未归档的公开内容；不能执行审核决定，不能访问私人内容。
- `ADMIN` 不能查看其他用户的邮箱；后台用户列表只使用 `id/nickname/role/createdAt`。`ADMIN` 也不能读取私人信件或私人记忆。
- 举报证据读取必须是独立、最小、受审计的流程；不得为任何后台角色增加私人内容的批量查询或导出。
- 角色授予/撤销只能由 `ADMIN` 执行，必须写审计；不能授予 `GUEST`，不能降级最后一个 `ADMIN`。
- 前端隐藏后台入口不构成权限控制；所有后台接口继续由 `SessionGuard + RolesGuard` 强制鉴权。
